# Источник НТД: «Техэксперт»/«Кодекс» — доступ и сверка актуальности

Зачем: сверка ссылок в проектной документации требует не только текстов норм, но и статуса
документа (действует / изменён / заменён / отменён) и действующей редакции. Тексты и статусы
живут в ИСС «Техэксперт»/«Кодекс»; открытый фонд статусов и реестров требований не даёт.

## Топология (чтобы не терять время на поиск)

- `docs.cntd.ru` — открытый электронный фонд: чтение текстов документов, бесплатно.
- `cntd.ru` — сайт вендора: продукты, контакты, заявки, техописания.
- Интранет-контур заказчика (у нас `ascrew.cntd.ru`) — «ИС Техэксперт: Интранет», документы
  под `/kodeks04/`, вход по логину/паролю рабочего места. Веб-доступ закрыт: корень отдаёт
  только «Техэксперт-Клиент», модуль кАссист и Кодекс-сервер; внутренних API-путей нет
  (`/api/*`, `/webservice/*` → 404). Работа только через клиент + модуль кАссист.
- Веб-версии новых продуктов (SMART Проектирование, Реестр требований) — отдельный контур
  (6 поколение), на интранет-сервере их обычно нет. Не искать их в интранете, запрашивать
  доступ отдельно.
- Ошибки на странице входа «Не найден пользователь с такой комбинацией логина и пароля» и
  «Исчерпан лимит лицензий для пользователей группы» — это лицензирование и группы на
  стороне вендора, а не пароль. Обращение к сервисному специалисту, а не повторный вход.

## Что реально автоматизирует сверку

| Инструмент | Что делает | Как поставляется |
|---|---|---|
| кАссист (kAssist) | Проверка проектной, рабочей, конструкторской, технологической и внутренней документации: выявляет отменённые/заменённые НД, расставляет и проверяет гиперссылки, пакетный режим по документам и каталогам, формирует отчёт | Модуль, встраивается в MS Office, LibreOffice, Adobe Acrobat Pro; интеграции с AutoCAD, Kompas-3D, ЛОЦМАН PLM |
| Kodeks API | Программный интерфейс для сторонних систем, «инструмент самостоятельной разработки» | По договору, документация публично не публикуется |
| «Реестр требований: Строительство» (входит в SMART: Проектирование) | База экспертно выделенных требований (связь с классификаторами КСИ, приказ Минстроя № 928, ПП № 1417), чек-листы, аудит проекта, сохранение перечня требований в файл | Отдельная подписка |
| СУ НТД | Внутренний фонд (СТО, ТУ, локальные акты), контроль актуальности ссылочных документов | Отдельное решение/внедрение |

## кАссист: подтверждённые факты о режимах и форматах

Источник — руководства пользователя кАссист 3.10 и 4.0.2, выложенные в открытом доступе
дилерами вендора (дилерские сайты ищутся по запросу «руководство пользователя кАссист pdf»).
Проверять факты под свою установленную версию, но рассчитывать на них можно.

| Что | Факт |
|---|---|
| Форматы в безинтерфейсном пакетном режиме | doc, docx, rtf, xls, xlsx, pdf — офисное приложение при этом не запускается |
| DWG | только интерактивно, через панель в AutoCAD (текстовое поле, ячейка таблицы); в безинтерфейсный пакетный список DWG не входит |
| Сканы PDF | «В отсканированных, а также отсканированных и распознанных документах работа кАссист **невозможна**» — только PDF, подготовленные редактором PDF |
| Отчёт | RTF, сохраняется вручную или по заданному пути; машиночитаемого формата (XML/JSON/CSV) нет |
| Расписание | есть внутри кАссист: вкладка «Пакетная обработка» → дата, время, периодичность (ежедневно / через интервал), опции сохранения файлов и отчётов |
| Вызов извне | командной строки, службы и API по каталогу в руководстве нет — внешний запуск не подтверждён |
| Логика пакетного прохода | одна подходящая ссылка — ставится автоматически; ничего не найдено или найдено несколько — файл уходит в список «требует внимания» и дорабатывается человеком |
| «Бессылочные» фрагменты | Inventor, Компас-3D (спецификация), Revit, SOLIDWORKS — часть объектов; в nanoCAD таблицы и таблица DWG |

**Куда девается работа агента.** Извлечение текста, OCR сканов, разбор DWG — делает агент своими
средствами; кАссист этого не умеет (сканы для него закрыты прямо). Что агент не может сам —
статус и действующую редакцию НД. Это и есть настоящий незакрытый вопрос сверки.

## Чек-лист запроса вендору

1. Документация Kodeks API: руководство программиста, спецификация методов, форматы обмена,
   точка входа, авторизация (логин/пароль, ключ, сертификат, привязка к IP).
2. Перечень методов: поиск документа, карточка и атрибуты, редакции и статус, ссылочные
   документы, изменения.
3. Позиции прайса: API, кАссист, Реестр требований, СУ НТД — что входит в действующий договор,
   что оформляется допсоглашением.
4. кАссист: запускается ли пакетная проверка **без ручного открытия файлов** (CLI, сервис,
   планировщик, API по каталогу) — по руководству ответ «нет, только окно модуля и его
   внутреннее расписание», нужно подтверждение для последней версии. Отдельно: подтвердить
   список форматов и формат отчёта (по руководству — doc/docx/rtf/xls/xlsx/pdf и RTF).
5. Экспорт перечней требований из «Реестра требований» и машинный API к нему
   (XML/JSON/XLSX/CSV).
6. Тестовый стенд или тестовая лицензия API на период отладки.
7. Сервисная (робот) учётная запись и правила её лицензирования — не только рабочее место
   пользователя.
8. Регламент сопровождения API и совместимость версий при обновлении системы.
9. Контакт технического специалиста по интеграциям.

Контакты: служба поддержки 8-800-505-78-25 (8:00–18:00 МСК), `spp@kodeks.ru` / `spp@cntd.ru`.
Демо-доступ 7 дней оформляется по ИНН компании.

## Питфоллы

- **Вендор отвечает «раскройте запрос» и «дать всё не можем».** В этом случае не пухнуть запрос, а
  срезать его до 5 пунктов, где каждый ответ — «да/нет»: программный доступ (адрес, авторизация,
  методы карточки документа, служебная учётка), внешний запуск кАссист и формат отчёта, лицензии
  и цена под эти два пункта, форматы документов и поведение на сканах, тестовый стенд + контакт
  техспециалиста. В письме писать прямо: «если пункт не закрывается — сообщите, скорректируем
  задачу». Остальное срезать самим.
- **Не ждать вендора там, где ответ лежит в открытом доступе.** Режимы, форматы и отчёты кАссист
  описаны в руководстве пользователя у дилеров; топология, факты и ограничения берутся из
  живых проверок. Прежде чем просить у вендора справку по возможностям — поискать её самому,
  а у вендора просить только то, что закрыто договором (API, лицензии, служебная учётка,
  тестовый стенд).
- **Вендорский .docx разбирать как OOXML, а не глазами.** `read_file` по .docx склеивает ячейки
  таблиц и теряет строки — для таблиц версий и режимов распаковывать пакет (`unzip` + разбор
  `word/document.xml` по `<w:tr>`/`<w:tc>` с учётом `gridSpan`/`vMerge`), иначе перечень
  приложений и версий читается неверно.
- **Не обещать автоматическую сверку, пока нет подтверждённого программного доступа.**
  Сначала проверить фактические точки входа (страницы, эндпоинты) и только потом говорить,
  что возможно.
- **Браузерная сессия агента изолирована от браузера пользователя** — авторизация пользователя туда
  не переносится. Пароли и коды не вводить и не запрашивать; доступ оформляется как отдельная
  учётная запись (лучше сервисная), проверяется живым вызовом, а не «должно работать».
- **Актуальность норм и текст проекта — разные проверки.** Корректно спроектированный узел
  со ссылкой на отменённый НД всё равно уходит в замечания.
- **Ссылок на пункты вендорских продуктов не выдумывать**: вендор публикует состав функций, но
  не публичные номера методов API — без полученной документации ссылаться не на что.
- **Перечень приложений ≠ перечень форматов.** Присланный вендором список «форматов» оказался
  приложениями и версиями, куда встраивается панель кАссист. Он не отвечает ни на вопрос о
  форматах файлов документации, которые модуль разбирает (включая сканы PDF), ни о формате
  отчёта, ни о запуске без GUI. Не выдавать его за подтверждение автоматизации — говорить прямо,
  что прислали не то, и добивать теми же вопросами.
- **Список поддерживаемых приложений описывает интерактивный режим.** Пока вендор не подтвердил
  CLI/сервис/API по каталогу, пакетная ночная проверка не подтверждена, сколько бы приложений ни
  было в списке.
- **Запрашивать полный методический материал, а не только приложения.** В нём режимы работы,
  форматы, отчёты и способ вызова; по Приложениям 1–2 судить о возможностях нельзя.
- **Сверять версии софта заказчика с таблицей.** AutoCAD/Revit/nanoCAD новее списка, ARCHICAD
  не 25, Inventor после 2021 — интеграции нет; это конкретное замечание до покупки, а не
  «уточнить у вендора».
